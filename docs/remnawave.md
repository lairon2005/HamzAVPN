# Установка Remnawave и подключение к боту

Инструкция проверена 03.10.2026 по официальной документации и коду Remnawave. Адреса, учётные записи и секреты своей установки храните в закрытых настройках, не в документации.

## Подготовка

Нужен отдельный сервер с Docker Engine и Compose plugin. Рекомендуемые ресурсы панели: 4 ГБ RAM, 4 CPU, 20 ГБ диска. Панель и бот используют отдельные базы данных; база панели не заменяет базу бота.

Создайте DNS-записи для панели и страницы подписки. HTTPS использует стандартный порт 443. Для автоматической выдачи сертификатов записи должны указывать на сервер reverse proxy. Пока DNS не обновился, первичную настройку можно выполнить через закрытый SSH-туннель.

Версии этой инструкции:

| Компонент | Образ |
|---|---|
| Панель | `remnawave/backend:3.4.4` |
| Страница подписки | `remnawave/subscription-page:8.0.0` |
| Нода, если нужна | `remnawave/node:3.4.1` |

У компонентов независимые номера версий. Перед обновлением изучите release notes, сохраните резервную копию базы и конфигурации. Не используйте изменяемый тег `latest` для воспроизводимого развёртывания.

## Панель

Скачайте официальный Compose и пример настроек из зафиксированного релиза:

```bash
sudo mkdir -p /opt/remnawave
cd /opt/remnawave
curl -fsSLo docker-compose.yml https://raw.githubusercontent.com/remnawave/backend/3.4.4/docker-compose-prod.yml
curl -fsSLo .env https://raw.githubusercontent.com/remnawave/backend/3.4.4/.env.sample
chmod 600 .env
```

Замените образ панели в Compose на `remnawave/backend:3.4.4`. Официальный Compose использует PostgreSQL 18.4 и Valkey 9 с Unix socket. Не переносите базы, ключи CA, пользователей и секреты из другого проекта.

В `.env` задайте:

- `PANEL_DOMAIN` — домен панели без схемы и пути.
- `FRONT_END_DOMAIN` — разрешённый Origin интерфейса, `https://` и домен панели.
- `SUB_PUBLIC_DOMAIN` — домен страницы подписки без схемы и завершающего слеша.
- `APP_SECRET` и `METRICS_PASS` — новые случайные секреты.
- `WEBHOOK_SECRET_HEADER` — случайная строка ровно 64 символа, латинские буквы и цифры.
- `POSTGRES_PASSWORD` и пароль внутри `DATABASE_URL` — одно новое случайное значение.

Не добавляйте секреты в команды с выводом, историю терминала, Git или логи. Пользовательское поле `FRONT_END_DOMAIN` не должно оставаться `*`, если интерфейс обслуживается на одном известном Origin.

Порты API 3000, metrics 3001 и PostgreSQL должны оставаться привязаны к `127.0.0.1`. Внешний доступ выполняется через reverse proxy. Не открывайте внутренние порты в интернет и не включайте режим разработки ради доступа к API.

```bash
docker compose config --quiet
docker compose up -d
docker compose ps
```

Перед публичным запуском reverse proxy создайте администратора, чтобы первичная регистрация не была доступна посторонним.

## Первичная настройка через SSH

Откройте туннель с явной привязкой к локальному интерфейсу. Вместо `<panel-ssh-alias>` используйте свою запись SSH config:

```bash
ssh -N -L 127.0.0.1:13000:127.0.0.1:3000 <panel-ssh-alias>
```

Туннель работает только пока открыта SSH-сессия. Для запросов к `http://127.0.0.1:13000/api` передавайте заголовки:

```text
Host: <домен панели>
X-Forwarded-For: 127.0.0.1
X-Forwarded-Proto: https
```

Это позволяет выполнить bootstrap через защищённое SSH-соединение, не меняя production-проверки Remnawave. Эти заголовки применяются только к приватному маршруту. Для публичной панели нужен настоящий HTTPS с проверяемым сертификатом.

1. `GET /api/auth/status`: проверьте `response.isRegisterAllowed`.
2. Если регистрация разрешена, `POST /api/auth/register` с JSON `username` и `password`. Пароль должен содержать минимум 24 символа, строчные/прописные латинские буквы и цифры.
3. Сохраните `response.accessToken` приватно. Для последующего входа используется `POST /api/auth/login` с теми же полями.
4. Запросы с административным JWT требуют одновременно `Authorization: Bearer <accessToken>` и `X-Remnawave-Client-Type: browser`. Без второго заголовка сервер возвращает 403.
5. После создания администратора проверьте `isRegisterAllowed=false`.

Если администратор уже существует, повторная регистрация не нужна. Не выполняйте сброс учётной записи при обычном повторном запуске установки.

## Токены интеграции

Создавайте отдельные токены для бота и страницы подписки. `GET /api/tokens/scopes` возвращает актуальный каталог прав установленной панели. Для создания токенов требуется административный JWT и заголовок `X-Remnawave-Client-Type: browser`; API-токен создать другой токен не может.

Пример `POST /api/tokens` для бота:

```json
{
  "name": "Subscription Bot",
  "expiresInDays": 365,
  "scopes": [
    "users:*",
    "hwid-user-devices:*",
    "internal-squads:read",
    "config-profiles:read",
    "system:read",
    "nodes:read"
  ]
}
```

Для страницы подписки достаточно:

```json
{
  "name": "Subscription Page",
  "expiresInDays": 365,
  "scopes": [
    "system:metadata",
    "subscription-page-configs:read",
    "subscriptions:read",
    "users:by-username"
  ]
}
```

Сохраняйте только значение `response.token` в закрытых `.env` соответствующих сервисов. У обычного API-токена запросы используют `Authorization: Bearer <token>`; заголовок типа браузера не требуется.

Контракт 3.4.4: имя от 2 до 30 символов, `expiresInDays` число не меньше 1, верхняя граница контрактом не установлена. Практически выбирайте целое разумное число дней и заменяйте токен до истечения срока. Если `scopes` пропущен, по умолчанию выдаются все права `['*']`; задавайте права явно. Неизвестные права сервер отклоняет.

## Страница подписки

Разместите сервис в той же Docker network, что и панель. Используйте образ `remnawave/subscription-page:8.0.0`, порт 3010 с привязкой к `127.0.0.1`, отдельный `.env` с правами 600:

```text
APP_PORT=3010
REMNAWAVE_PANEL_URL=http://remnawave:3000
REMNAWAVE_API_TOKEN=<отдельный токен страницы>
TRUST_PROXY=1
```

`TRUST_PROXY=1` подходит для одного reverse proxy. При другой схеме укажите фактическое число доверенных переходов или доверенные адреса согласно официальной инструкции. Приложение не должно быть доступно напрямую извне.

Reverse proxy обслуживает страницу в корне её отдельного домена, а не под произвольным подпутём. Ссылка пользователя имеет форму `https://<домен подписок>/<shortUuid>`.

Для панели и страницы proxy передаёт `Host`, `X-Forwarded-Proto`, `X-Forwarded-For`, `X-Real-IP`, а при необходимости `X-Forwarded-Host` и `X-Forwarded-Port`. Внешний HTTPS 443 использует действительный сертификат. После изменения `.env` пересоздайте соответствующий контейнер, обычного restart недостаточно.

Настройте бренд через административные API или интерфейс:

- `PATCH /api/remnawave-settings`, объект `brandingSettings` с `title` и публичным HTTPS `logoUrl`.
- `GET /api/subscription-page-configs`, затем `GET /api/subscription-page-configs/{uuid}`.
- `PATCH /api/subscription-page-configs` с `uuid`, `name` и полным обновлённым `config`. Сохраните инструкции приложений и SVG-библиотеку. Замените `brandingSettings.title`, `logoUrl`, `supportUrl`, а также `baseSettings.metaTitle` и `metaDescription`.
- У блоков установки `svgIconColor` может быть `#163b75`. Глобального `theme`/`primaryColor` поля в конфигурации этой версии нет.
- Проверьте тексты всех включённых языков. Контакт поддержки должен вести в личное обращение.

## Профиль, группа и ноды

Для установки ноды на сервере панели используйте [инструкцию совместного размещения](remnawave-node.md): она описывает общий порт 443, локальный TLS-сайт, PROXY protocol и независимую доступность панели.

При первом старте Remnawave создаёт Default-Profile и Default-Squad. Они являются техническими заготовками: для реальных подключений нужны работающая нода, соответствующий inbound и публичный host.

- `GET /api/config-profiles` → `response.configProfiles`, каждый профиль содержит `uuid` и `inbounds[].uuid`.
- `GET /api/internal-squads` → `response.internalSquads`.
- `POST /api/config-profiles`: `{"name":"<название>","config":<объект Xray>}`.
- `POST /api/internal-squads`: `{"name":"<название>","inbounds":["<uuid inbound>"]}`.

Ноды обслуживают пользовательские подключения, панель управляет ими. Для ноды используйте её отдельную официальную инструкцию. `GET /api/keygen` выдаёт `response.secretKey` — пакет сертификатов/ключей для доверия между панелью и нодой. Не заменяйте его произвольным паролем и не публикуйте.

При создании ноды `POST /api/nodes` передайте `name`, `address`, внутренний `port`, а также `configProfile.activeConfigProfileUuid` и `configProfile.activeInbounds`. Внутренний порт управления нодой должен быть доступен только панели. Образ ноды использует `NET_ADMIN`; соблюдайте официальный Compose выбранной версии.

Публичный host создаётся через `POST /api/hosts`: обязательны `inbound.configProfileUuid`, `inbound.configProfileInboundUuid`, `remark`, `address`, `port`. Для HTTPS/TLS используется 443; параметры транспорта, `sni`, `host`, `path` должны совпадать с реально настроенным подключением. Поле `nodes` связывает host с нодами, `internalSquads` задаёт доступные группы. Не публикуйте host, пока нода и сертификаты не проверены.

## Подключение бота

В закрытых настройках бота укажите:

```text
REMNAWAVE_API_URL=https://<домен панели>
REMNAWAVE_API_TOKEN=<отдельный токен бота>
REMNAWAVE_DEFAULT_SQUAD_UUID=<uuid группы с рабочими inbounds>
REMNAWAVE_SUB_HOST=<домен страницы подписки>
```

Значение API URL не содержит `/api`: клиент сам добавляет пути запросов. Пересоздайте контейнеры бота и сайта после изменения настроек. Проверьте доступ из контейнеров, а не только из SSH-сессии на сервере.

Версия 3 использует числовой `id` пользователя. В ответах также присутствуют `username`, `shortUuid`, `subscriptionUrl`, `vlessUuid`, `activeInternalSquads`, `userTraffic`. Клиент должен использовать `id` для действий пользователя и устройств; `vlessUuid` относится к протоколу и не заменяет `id`. `PATCH /api/users` принимает `id` или `username`. Устройства используют `userId`. При обновлении `expireAt` дата должна быть в будущем; истекшую подписку отключайте соответствующим действием.

## Проверка

1. Контейнеры панели, базы, Valkey и страницы подписки работают без постоянных перезапусков.
2. Сертификаты панели и подписок проходят обычную проверку TLS без отключения проверки.
3. Токен бота получает profiles/squads и выполняет создание/обновление тестового пользователя.
4. Тестовый пользователь входит в нужную группу, получает ссылку на правильный домен.
5. Страница подписки отображает название, логотип и личную поддержку.
6. Подписка в клиентском приложении содержит только работающие настроенные hosts. Проверьте фактическое подключение через ноду.
7. Удалите только созданного для проверки пользователя и проверьте отсутствие случайных тестовых продаж.
8. Сохраните резервную копию настроек с закрытым доступом, установите обновление сертификатов и проверяйте срок API-токенов.
