# Развёртывание и HTTPS

Создайте `.env` из `env.dist`; храните секреты только в этом файле. Укажите собственный `DOMAIN` без схемы и пути. База, бот и сайт запускаются в отдельном Compose-проекте `hamzavpn`.

## Первый запуск во время обновления DNS

1. Установите Docker Compose, Python 3, Certbot, OpenSSL, `dig` и `flock`. Порты 80 и 443 должны быть свободны и доступны извне.
2. В действующей DNS-зоне настройте A основного домена на новый сервер. До первого выпуска сертификата запись должна работать в режиме **DNS-only**, без проксирования Cloudflare. Для описанного IPv4-развёртывания удалите AAAA основного домена. При изменении NS проверяйте делегацию у регистратора: записи в новой зоне начинают действовать после смены делегации.
3. Установите в `.env` `CERT_DIR=/etc/letsencrypt`. Не добавляйте этот каталог или `.env` в Git.
4. Соберите образ, запустите базу, примените схему и запустите бот и сайт:

   ```bash
   docker compose build vpn_bot
   docker compose up -d --wait postgres
   docker compose run --rm --no-deps vpn_bot python3 fix_db.py
   docker compose up -d --no-deps vpn_bot vpn_site
   ```

5. До получения сертификата используйте отдельный HTTP-контейнер с именем `hamzavpn_bootstrap`. Он должен слушать порт 80, проксировать публичные страницы сайта и обслуживать `/.well-known/acme-challenge/` из каталога `certbot/data` проекта. Не включайте перенаправление challenge-запросов на HTTPS. Сохраните этот контейнер после остановки: скрипт сможет вернуть его при неудачном запуске HTTPS.
6. В защищённом системном файле вне репозитория задайте `PROJECT_DIR` — абсолютный путь к проекту, и `ORIGIN_IPV4` — IPv4 нового сервера. Передайте эти переменные службе systemd, которая запускает `scripts/enable_tls.sh` от root. Таймер может повторять запуск раз в несколько минут; одновременные запуски исключены блокировкой файла.

Скрипт читает `.env` как данные. Если Google DNS или Cloudflare DNS ещё возвращает другой адрес, несколько адресов либо AAAA, он печатает `TLS pending DNS` и завершает работу без обращения к удостоверяющему центру.

После совпадения A скрипт получает сертификат только для основного домена через HTTP-01. Он создаёт в `/etc/letsencrypt` ссылки `fullchain.pem` и `privkey.pem` на файлы `live/<DOMAIN>/`; весь каталог монтируется в nginx, поэтому цели ссылок доступны. Уже доверенный сертификат с подходящим именем и сроком более семи дней используется повторно.

Конфигурация nginx проверяется до остановки HTTP-контейнера. Затем запускается только сервис nginx этого проекта на 80 и 443. Если запуск HTTPS не удался, возвращается `hamzavpn_bootstrap`. Контейнеры базы, бота, сайта и других проектов скрипт не останавливает.

## Продление и Cloudflare

Включите штатный `certbot.timer`. Сохраните доступ к HTTP-01 из `certbot/data`; после успешного продления перечитайте nginx через deploy-hook:

```bash
docker compose exec -T nginx nginx -s reload
```

Hook должен выполняться из каталога проекта либо с явными `--project-directory`, `--env-file` и `-f`. Проверяйте срок сертификата и результат продления.

После успешного первого запуска можно выключить таймер первоначального включения HTTPS. Если потребуется проксирование Cloudflare, включайте его с режимом **Full (strict)** и действующим сертификатом сервера. Убедитесь, что правила Cloudflare пропускают HTTP-01 для последующего продления. Проверка A в `enable_tls.sh` предназначена для режима DNS-only; проксированная запись эту проверку не проходит.

Mini App можно разместить на `/tma` основного домена. Отдельный поддомен требует собственной DNS-записи, покрытия сертификатом и соответствующей настройки приложения в BotFather.

Проверьте публичные страницы `/privacy`, `/terms`, `/support`, `/tariffs` и Callback URL `/platega` через HTTPS до отправки проекта на согласование. Проверка кассы описана в [инструкции Platega](platega.md).
